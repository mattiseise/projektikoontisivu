Start here · the big picture before week 36

Parlar Ioniano: what you build and how you proceed

You build Parlar Ioniano, a public website that presents Ionian (Lingua Ioniana), the language you created, with hand-written HTML, CSS and JavaScript and the Bootstrap component library: every grammar table is loaded from a JSON file that you have checked against your own 58-page reference PDF. A curious learner opens the public URL on a phone or a laptop, finds how a letter is pronounced, reads the pronoun and article tables, converts numbers and learns the café dialogue, and another person can get the project running from your README alone.

You decide how each page is built, you write every expected test result before the run, and you are the only one who can check the language content against the PDF. The licence of the code, the institution's device-security policy line, your public author name and the external testers are agreed with the supervisor, not decided by you or by AI.

How to use the weekly guide

  1. Open only the current week. Read how the week connects to the whole project, and the week goal.
  2. Do the week's work steps in order. The first unfinished work step is open. Tick a part as soon as you have done it: a tick is your own memory, not a submission.
  3. When a work step changes the site, do each change as a GitHub issue and work through it with the six steps on the Working method page. One work step can need several issues.
  4. Do the end-of-week check. Write the three project journal fields (what and how, why, where the work sample is), download the whole journal and commit it as project-docs/project-journal.md, replacing the old file.

Work step is one numbered item in this site's weekly guide. GitHub issue is a numbered card in your repository for one change to the site, with a done-when condition and a size estimate. It is usually half a day to a day of work, and the commit that finishes it closes it. Working method is the six steps on the Working method page (pick, plan, build, test, save, log) that you repeat for every issue.

Site parts and tools
Your reference PDF (58 pages)
The only source of truth for the language content. You type every form from it and check the site against it: no AI and no other person knows Ionian, so an invented form is a bug.
Your project folder and its repository
The project folder on your own machine, whose whole history Git stores, and its public copy on GitHub. The page files are in the root, your own code in css/ and js/, the language data in data/, the unit tests in tests/ and your documents in project-docs/. There is no build step: the files you write are exactly the files that go live.
Language data data/*.json
JSON is a plain-text format for structured data (JavaScript Object Notation). Every grammar table, word and phrase is stored here and loaded with fetch(), the browser call that loads a file while the page is open. tools/check-data.html checks every file.
Your JavaScript js/
One shared loader in js/data.js, one reusable table function, the converter as pure functions in js/numbers.js and one script per page. Elements are built with textContent, never with innerHTML and data. Most function names in the implementation help are suggestions.
Bootstrap from a CDN
Bootstrap is the component library for the navbar, the grid, the tables, the tabs, the cards and the accordion. It is loaded from a content delivery network (CDN), a public server that hosts its files, with a pinned version and an integrity hash, and themed in css/style.css. Bootstrap Icons and the font come the same way. The number converter is built by hand without Bootstrap components.
Local web server (Live Server)
fetch() works only over http://, a page served by a server, never over file://, a file opened straight from disk. So you always open the site through Live Server at http://localhost.
Tests
A unit test is a small automated check that runs one of your functions and compares the result with the value you wrote down beforehand. The converter's unit tests run in the browser from tests/tests.html, and every test case, automated or by hand, is a numbered row in project-docs/test-matrix.md.
Git, GitHub and GitHub Pages
GitHub issues, small commits, the tags v0.5 and v1.0, and a short feature branch for the week-45 feedback change. GitHub Pages publishes the main branch at your public URL over HTTPS.
AI
May help with HTML, CSS and JavaScript, error messages and test ideas, and every significant use goes into the AI log. It never writes Ionian content. The site structure, the accessibility solutions and the converter logic are your own work.

What is assessed in the demonstration?

This one project is the demonstration for four qualification units: Tieto- ja viestintätekniikan perustehtävät (25 competence points), Ohjelmointi (45), Ohjelmistokehittäjänä toimiminen (45) and Ohjelmiston toteuttaminen ohjelmistokomponenttikirjastolla (30), 44 assessed requirements in total. The codes t1–t12, p1–p11, s1–s14 and k1–k7 refer to these four units in this order, and all 44 rows are in the Evidence matrix view.

You learn and show how to set up a real toolchain, the tools a project is written, tested and published with, and publish through it; how to write structured, maintainable and tested JavaScript; how to plan work as GitHub issues, estimate it and review it with a client; and how to choose a component library on measured evidence and build an accessible site on it. Nothing is assessed separately: every requirement is proved by the work you do in these weeks and by the work sample it leaves behind, for example a commit (one named, saved change in the repository's history), a memo or a test row. The language itself is your own source material: the demonstration assesses your web development skills.

The qualification units also include competencies that are demonstrated in a team. That is why the work steps talk about a client, reviews and agreements even though you build this project alone. The supervising teacher acts as the client's representative and as the supervisor, and the agreements, reviews and shared decisions are held with them or with another person the supervisor agrees. Those conversations are assessed competence in their own right, not a formality.

Original brief · given 31 Aug 2026

A website for a language that exists nowhere else

I have spent years building a language. Ionian — Lingua Ioniana — is a Romance language with its own alphabet, three genders, its own numbers and its own café small talk. Right now it lives in a 58-page reference PDF that only I can navigate. I want a website where a curious learner can actually find things: how a letter is pronounced, how the pronouns change when you talk to a friend or a stranger, which article goes with which gender, and how to count to ten thousand.

Accuracy matters more than volume. No AI and no other person knows this language, so every table on the site must be checked against my PDF — an invented form is a bug. My terms of use stay visible: the material is mine, it is shared to spread awareness of Ionian, and the site credits me as the author. Where my PDF is still under construction, the site says “coming later” instead of making content up.

At the end of October I want to try a half-way version at a real web address on my own phone, and I will bring along a tester who has never seen Ionian. I want to hear, in their words, whether they can find the alphabet, read a pronoun table and understand what this language is — without me explaining anything.

By the fourth of December I want version 1.0 at a public URL: a site with a number converter I can show off, a phrasebook where a beginner can learn my café dialogue, and a README good enough that another person can get the project running without asking me anything.

Agreed implementation

Hand-written HTML, CSS and JavaScript — no build step and no bundler. A bundler is a tool that packs many source files into one file for the browser; this project has none, so the files you write are exactly the files that go live. Bootstrap is the component library, loaded from a content delivery network (CDN) — a public server that hosts Bootstrap's files so you link to them instead of copying them into your repository — and compared and configured in week 38: the navbar, tables, tabs, cards and accordion build on it, and the number converter page is built from scratch without it. All content lives as JSON in data/ and is fetched at runtime through one shared loader in js/data.js. This data store is the agreed implementation, because every later page is built on it: in week 37 you justify the agreed choice against at least one alternative, and if the comparison clearly favours another option, the deviation is agreed with the supervisor before the next implementation week. Your decision: which Bootstrap components you build on and where you write your own CSS (week 38). Unit tests run in the browser from tests/tests.html. Published on GitHub Pages from the main branch — a branch is a named line of commits, and main is the one Pages serves. “The public URL” on this site always means that Pages address: the web address (URL) anyone can open, not a file on your own laptop.

Priorities. P0 is the must-have core that has to be finished; P1 is important follow-up work, started only once P0 works; P2 is an optional extra that may be dropped without failing the project.

Requirement · P0 minimum: Home · Alphabet & Pronunciation · Pronouns · Nouns, Articles & Gender · Numbers + converter · Phrasebook & Chapter 1.

Named temptations that are not in this project: an interactive verb conjugator, audio recordings, user accounts, and content for the PDF's under-construction pages 57–58 — the site says “coming later”. The Verbs overview (P1) may start only if P0 is complete by the end of week 46.

Working method · one GitHub issue at a time

Six steps, every time

This is the working method for one change to the site. The weekly guide tells you which work steps to do this week. Inside a work step that changes the site, repeat these six steps for every GitHub issue, then go back to the work step and tick its parts.

  1. 1Pickone GitHub issue from the top of the backlog
  2. 2Planwhich file and which data
  3. 3Buildpiece by piece
  4. 4Testagainst your own PDF
  5. 5Savecommit and push
  6. 6Logresult in the issue, takeaway in the journal

Rule of thumb: if you cannot explain the change, the work is not done yet.

Open only the current week. Read how the week connects to the whole project and the week goal, do the work steps in order, then do the end-of-week check and fill in the week's project journal.

Agreements with the supervisor go where they belong: a decision and its reason into the plan, a change to the site onto its GitHub issue. In the repository, people appear only by role, for example supervisor or tester A.

Test like a developer

Testing is not just clicking around. Record the expected result, the observed result, the cause of the bug, the fix and the re-test.

  • At least 12 planned test cases with the expected result written before the run — thirds: normal use, limits, error cases. The test cases are numbered T01, T02, T03 and so on in project-docs/test-matrix.md, and that number is how a test is referred to everywhere else on this site, also in the names of your unit tests.
  • 3 complete debugging chains: observation → reproduction → cause → fix commit → re-test → regression test.
  • The broken-network case: block a data JSON in DevTools and expect your own error state, not a blank page.
  • The converter's junk inputs: empty, letters, negative, too large — decide the behaviour and write it down.
  • The search's cross-site scripting (XSS) string — text that would run as code if the page inserted it as HTML — renders as harmless text because you used textContent; prove it on the public URL.
  • The released version is tested in a clean environment, never only in your own working folder.

                        Pre-filled · included in the downloaded file

                        1 · Concept

                        A public reference site for Ionian (Lingua Ioniana), a constructed Romance language. Hand-written HTML, CSS and JavaScript with no build step; Bootstrap from a CDN as the component library; all grammar content as JSON under data/, fetched at runtime — the source of truth is the author's reference PDF. Published on GitHub Pages. The whole project is in English.

                        2 · Site map and scope

                        P0: Home · Alphabet & Pronunciation · Pronouns · Nouns, Articles & Gender · Numbers & Comparison with the converter · Phrasebook & Chapter 1. P1 (only if P0 is done by the end of week 46): Verbs overview. P2: Word-building. Out: conjugator, accounts, audio, PDF pages 57–58.

                        7 · Data (agreed implementation)

                        Content JSON is loaded at runtime with fetch() from data/ through one shared loader in js/data.js — so the site is always opened over http://, never file://. This data store is the agreed implementation, because every later page is built on it. In week 37 you justify the agreed choice against at least one alternative. If the comparison clearly favours another option, the deviation is agreed with the supervisor before the next implementation week. Loading and error states are implemented in week 37 and proven in week 39. Every content file is checked against the reference PDF — an invented form is a bug. A broken-network response is a test case.

                        8 · Quality bar

                        At least 12 planned test cases with the expected result written before the run and executed from tests/tests.html in the browser, 3 complete debugging chains, an accessibility pass with Lighthouse before/after pairs, an HTML validation pass, a client review in week 44 and an external user test in week 48.

                        9 · Roles

                        The student is the developer AND the client in the language creator's role. The supervisor acts as the client's representative: they receive the kickoff questions and represent the client in the reviews. The external tester is a different person who has never seen Ionian. In the repository, people appear only by role (supervisor, tester A); names go to the supervisor in Teams if they are needed.

                        10 · Open items — the supervisor owns these

                        License of the code · the institution's device-security policy line (t12). An empty field is the correct result until these are agreed.

                        Open items are not filled in by the student or by AI. They are agreed with the supervisor and updated into the plan afterwards.

                        AI is an allowed tool · understand, verify, test, log

                        You make the decisions.
                        AI is a tool.

                        AI may help you with HTML, CSS and JavaScript, error messages and test ideas — logged, verified and tested. It cannot help you with the content: no model knows Ionian. Every grammar table, every phrase and every expected test result comes from your own PDF and is checked against it. The site structure, the accessibility solutions and the number converter logic are your own work — that is what the demonstration assesses.
